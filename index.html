2. Individual RAG app + technical research

Reader task and scope

IT Docs Navigator will help an IT student or junior technician answer small Docker deployment questions from a deliberately limited source collection. The first version covers ports, persistent data, bind mounts, bridge networking and Dockerfile instructions.

The user should be able to ask a plain-language question, inspect the passages used, receive a concise source-supported answer and open the original source. It is an explanation tool; it will not execute suggested commands or inspect private machines.

Research comparison and architecture choice

ApproachRepresentation and useBenefit to investigateMain limit
Keyword baselineSQLite FTS5/BM25 matches words and commandsStrong reference point for exact flags such as EXPOSEWording changes can miss relevant content
VectorReal text embeddings and similarity searchMay retrieve a paraphrase such as keeping files after a container is replacedSimilarity is not proof of correctness; requires compatible model/index configuration
GraphEntities and typed edges with supporting passages; Neo4j is a researched native graph optionMay help explicit resource relationships or multi-step questionsEntity extraction, ambiguity and unsupported edges add work
CombinedKeyword and vector results; optional bounded graph expansionCould combine exact-term and semantic evidenceMore moving parts; benefit must be observed on the same questions

Chosen approach: vector retrieval plus an FTS5 baseline/hybrid comparison, using SQLite with the sqlite-vec extension. Study and sketch graph modeling, but keep native graph storage and automated entity extraction outside the first hosted version. The selected questions are mostly answered by short passages, so a full graph database is not yet justified. Qdrant and Neo4j are alternatives, not additional services being deployed.

Why SQLite, Rust and NATS: Derrick asked to use the classroom technologies. SQLite keeps this small corpus on one host; NATS JetStream will retain import jobs; a small Rust worker will process those jobs and write the retrieval database. For five documents a direct Python importer would be simpler. The additional queue/worker is a bounded learning choice, to be kept only if it can be checked without delaying the hosted RAG journey.

Technical facts and intended settings

  • SQLite FTS5 provides lexical search and BM25 ranking. sqlite-vec is a separate vector extension; vanilla SQLite does not generate embeddings or provide a native graph database.
  • Proposed embedding model: sentence-transformers/all-MiniLM-L6-v2, 384 dimensions, Apache-2.0. Its default input limit is 256 word pieces. Preserve model revision, tokenizer and normalization settings; keep chunk text plus heading within the verified limit. Use the same model for questions.
  • Proposed generation provider/model: Google Gemini Developer API, gemini-2.5-flash-lite, contingent on free-tier access and availability. Published pricing shows a free tier; access, quota and suitability for this account are untested. Derrick has no API set up. Keep billing disabled, keys on the server and all submitted context public.
  • NATS Core Pub/Sub does not retain missed messages. JetStream supplies persisted delivery with acknowledgments/redelivery. Application-level idempotency is still required; do not claim exactly-once end-to-end imports.
  • SQLite WAL permits concurrent reading and writing but only one writer at a time, with same-host constraints. NATS does not replicate the SQLite file or make it a distributed database.

These are documentation-supported capabilities and proposed settings, not measured performance of this app. Exact dependency versions/model revisions will be pinned after a compatibility check.

Proposed import and question flow

Import: admit only allowlisted, permitted documents; remove navigation; retain headings/code blocks and original source locations; hash originals and prepared text; split text; generate real embeddings; then have the Rust worker perform one short transaction updating source/chunks/FTS/vector records. Emit an index-ready event after commit and acknowledge the job after durable completion. An outbox/replay strategy and stable job IDs handle the commit/publish gap; duplicate deliveries must leave one current source version.

Question: validate length and apply access rules; generate the compatible query embedding; retrieve current public passages; compare vector results with FTS5 and a rank-fusion option; select a small context; close database reads before waiting for generation; request an answer supported only by that context; return references to the original document and section. Initial responses can use ordinary HTTP. Cross-device stream replay, answer fan-out and multiple replicas are deferred.

Ownership boundary: only the worker writes the new rag.sqlite3 retrieval database. Existing FastAPI authentication uses its own database and remains separate. No claim is made that the current account database already supports this RAG workflow.
